# Bulletin Board Merkle Tree (SHA-256, RFC 9162)

**Status:** Draft
**References:** RFC 9162 §2.1, Design Spec sections 2.7, 6.3

---

This document is the authority for the SHA-256 (public) tree of the bulletin board. The Go implementation (`crypto/merkle`), the board service and the browser verifier all implement it. The Poseidon SNARK tree is out of scope; see `deduplication.md`.

The tree is the RFC 9162 §2.1 Merkle tree, without modification.

## 1. Hashes

All hashes are SHA-256 (32 bytes). `‖` is concatenation.

| Name | Definition | RFC 9162 |
|---|---|---|
| Leaf hash | `SHA-256(0x00 ‖ d)` | §2.1.1 |
| Node hash | `SHA-256(0x01 ‖ left ‖ right)` | §2.1.1 |
| Empty root | `SHA-256("")` (hash of the empty string) | §2.1.1 |

The `0x00` / `0x01` prefixes domain-separate leaves from interior nodes, so an interior node can never be presented as a leaf.

For a ballot, `d` is the leaf encoding `u32be(len)‖ballot_id ‖ u32be(len)‖encrypted_ballot ‖ u32be(len)‖zk_proofs` (see `layer2-ballots.md` §1.2).

## 2. Tree head

For an ordered list `D[n] = {d(0), …, d(n-1)}`, the tree head `MTH(D[n])` is:

- `n = 0`: the empty root.
- `n = 1`: `SHA-256(0x00 ‖ d(0))`.
- `n > 1`: `SHA-256(0x01 ‖ MTH(D[0:k]) ‖ MTH(D[k:n]))`, where `k` is the **largest power of two strictly less than `n`**.

An unpaired last node is never duplicated or padded. The shape of the tree is therefore determined by `n` alone, and two trees of different sizes never share a root.

## 3. Inclusion proof

- **Generation:** `PATH(m, D[n])` (RFC 9162 §2.1.3.1), the list of sibling hashes from the leaf up to the root.
- **Verification:** RFC 9162 §2.1.3.2. The verifier is always given the leaf hash, the leaf index `m`, the tree size `n`, the proof and the expected root.

Verification fails if any of the following holds:

1. `m >= n`.
2. The proof is longer or shorter than `PATH(m, D[n])` for that `(m, n)`.
3. The computed root differs from the expected root.

## 4. Consistency proof

- **Generation:** `PROOF(m, D[n])` / `SUBPROOF` (RFC 9162 §2.1.4.1), proving that the head of the first `m` leaves is a prefix of the head of `n` leaves.
- **Verification:** RFC 9162 §2.1.4.2, given `size1`, `size2`, `root1`, `root2` and the proof.

Conventions this specification adds beyond the RFC text:

- `size1 > size2` is rejected.
- `size1 == size2` requires an empty proof and `root1 == root2`.
- `size1 == 0` requires an empty proof, and `root1` must be the empty root.

## 5. What this does not prove

A consistency proof shows that one tree head extends another. It cannot show that the board served **everyone** the same history. A board that presents different, individually consistent histories to different parties (a split view) is not detected by any single proof.

Fork detection therefore relies on monitors comparing signed tree heads with one another and with the voter-facing verifier ("gossip"). RFC 9162 §11.3 (Misbehaving Logs) describes both the split-view behaviour and the comparison of signed tree heads as the detection technique, and notes that the gossip mechanism itself is not defined by the RFC.

## 6. Encodings

- Hashes in JSON, APIs and test vectors are **lowercase hex**, 64 characters.
- Test vectors: `crypto/vectors/testdata/merkle.json`, generated by `go test ./vectors/ -run TestGenerateMerkleVectors -update`. Every implementation (Go and browser) must reproduce them.
