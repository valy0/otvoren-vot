Otvoren-Vot · End-to-End Verifiable E-Voting

Online Voting Flow

From voter authentication through eAuth 2.0 to encrypted ballot submission, identity stripping, Merkle tree inclusion, and browser extension verification — a complete end-to-end journey.

Phase 1 — Authentication
1
Voter opens izbori.bg/vote
Browser
Browser redirects to Auth Service → SAML 2.0 / OIDC redirect to Bulgarian eAuth 2.0 identity provider. Voter authenticates with national credentials + MFA.
2
eAuth assertion → Session token
Auth Service
Auth Service validates the assertion, extracts ЕГН, checks electoral roll eligibility, and issues a signed JWT (30 min TTL) via HttpOnly cookie.
session_token = { egn_hash: SHA-256(ЕГН), election_id, session_nonce: random(256-bit) }
Phase 2 — Extension Binding (Malware Defense)
3
Blinded session token handoff
Extension
Page JS blinds the session token via RSA Blind Signatures (RFC 9474), gets it signed by Collection Server, unblinds, and passes {signed_token} to the extension. The extension authenticates to the Verification Service — which validates the signature but cannot link the token to any voter.
4
Code mapping delivered to extension
Verification Svc
3-of-5 verification trustees each compute partial codes using their key shares. Combined into a per-session mapping: {party → 6-digit code}. Delivered to extension's background worker — invisible to page JS.
{ "Party A": "482917", "Party B": "103856", "Party C": "739201", ... }
Phase 3 — Client-Side Encryption
5
Voter selects party + candidate
Browser
The browser performs all cryptographic operations client-side:
1. Generate ballot_id = crypto.getRandomValues() → 256-bit random
2. Encrypt using ElGamal / Ristretto255 via libsodium.js WASM
   → Party vector: one Enc(1) for selected, Enc(0) for rest
3. Generate ZK validity proofs (Sigma protocol):
   → Each element is Enc(0) or Enc(1), party vector sums to exactly 1
4. Deterministic nonces from HKDF(signed_token) for verification codes
Phase 4 — Submission + Identity Stripping
6
Submit to Collection Server
Collection Svc
Browser sends {ballot_id, encrypted_ballot, zk_proofs} with session token. Collection Server validates session, checks eligibility, enforces rate limits (10/hr per voter), records identity-to-ballot mapping.
→ Record: egn_hash → ballot_id (private Layer 1 DB, sealed at poll close)
→ Re-vote: upsert — previous ballot_id moved to history table
7
Strip identity → Forward to Layer 2
Collection Svc
Collection Server builds a new forwarding payload with all identity removed:
ЕГН / egn_hash — never sent to Layer 2
Session token / nonce — never forwarded
Client IP address — request originates from Collection Server
HTTP headers — User-Agent, Accept-Language, all removed

→ Forward: { ballot_id, encrypted_ballot, zk_proofs } — nothing else
8
Validate proofs, append to Merkle tree
Bulletin Board
Independently validates all ZK proofs (ballot validity + candidate validity). Appends to dual-hash Merkle tree (SHA-256 + Poseidon/BN254), computes new root, signs it, returns inclusion proof.
→ Append at position N in dual Merkle tree
→ Return: { merkle_root, inclusion_proof, position }
Phase 5 — Receipt + Verification Code
9
Voter receives receipt
Browser
Collection Server returns the Merkle inclusion proof. Voter can save their ballot_id for post-election verification at verify.izbori.bg.
Receipt: { ballot_id, merkle_root, inclusion_proof }
→ Proves ballot exists in the tree — reveals nothing about content
10
Return code verification in extension popup
Extension
Verification Service derives a return code from the encrypted ballot (via 3-of-5 threshold trustees), sends it to the extension. The extension compares against the pre-loaded code mapping and shows the result — completely isolated from page JavaScript.

✓ Codes Match

The return code matches the expected code for the selected party. The correct ballot was encrypted, transmitted, and recorded. The voter can trust the result even if the voting page was compromised by malware.

✗ Codes Mismatch

Possible malware altered the vote before encryption. Voter should: (1) Re-vote from a different device, (2) Vote in person at a polling station, (3) Report to the election commission.
